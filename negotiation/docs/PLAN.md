## 1. 확정한 협상 규칙

2026-11-16에 사용자가 제안대로 확정했다. 같은 날 사용자 승인으로 "거절 이후 가치" 규칙과 공급사의 숨은 마감 범위를 수정했다(8절). 수치는 설명용 가정이며 `default_buyer_private()`와 `PolicyConfig`에서 바꿀 수 있다.

| 질문 | 규칙 | 이유 |
|---|---|---|
| 역제안을 보내면 상대의 기존 제안은 철회되는가 | 기본은 **소멸**. 상대가 유효 라운드를 명시한 제안(`valid_through_round`)만 유지 | 역제안에 위험이 없으면 "끝까지 역제안"이 항상 최선이 되어 수락 판단이 의미를 잃는다 |
| 거절되면 다음 라운드인가 종료인가 | 상대 응답은 수락·재제안·종료 셋 중 하나. 재제안이면 다음 라운드로 간다 | 마지막 기회에 거절되면 대안 견적으로 끝난다 |
| 협상 길이 | 최대 5라운드. 공급사는 자기만의 숨은 마감(2~5라운드)을 갖는다 | 상대 마감이 숨겨져 있어야 결렬 위험이 생긴다 |
| 대안 견적의 유효기간 | 협상 전체 기간 동안 유효로 고정. 만료 라운드 필드는 둔다 | 만료 시나리오는 후속 확장 |
| 협상 마감과 납기 제한 | 협상 마감은 라운드 수, 납기는 별도. 납기 30일 초과는 **절대 금지**, 선호 납기 14일 | 금지 조건은 비용으로 환산하지 않고 예외로 처리한다 |
| 결제일 환산 | 금액 × 연 6% × 결제일수 ÷ 365 만큼 총비용에서 차감 | 늦게 낼수록 우리 자금 비용이 준다 |
| 납기 환산 | 선호 납기를 넘는 하루당 2만 원 가산 | 재고·일정 위험의 단순 근사 |
| 라운드·승인 비용 | 라운드당 1만 원, 승인 1건 3만 원을 비교식에만 반영 | 0으로 두면 승인 요청과 추가 라운드가 공짜가 된다 |
| 거절 이후 가치 | `(1 − 최종안일 가능성) × max(공급사의 다음 제안 예상 절감액, 다음 라운드에 낼 수 있는 양보안의 기대값)`. 마지막 공개 라운드는 항상 최종으로 본다 | 공급사는 계속 양보한다고 보되, 상대 제안이 최종안이면 거절이 곧 결렬이다. **근사**이며 다회 협상의 최적 전략이 아니다 |

### 권한 3단계 (기본값)

| 단계 | 단가 | 납기 | 결제일 | 환산 총비용 |
|---|---|---|---|---|
| 자동 실행 | 10,600원 이하 | 21일 이하 | 납품 후 30일 이상 | 1,060만 원 이하 |
| 승인 후 실행 | 10,900원 이하 | 30일 이하 | 0일 이상 | 1,084.5만 원 이하 (대안 견적보다 유리) |
| 실행 금지 | 위 범위 밖 전부 | | | |

대안 견적은 단가 10,900원·납기 14일·결제 30일이며 환산 총비용은 약 1,084.6만 원이다. "납품 즉시 결제"는 공급사에게 유리한 교환 카드지만 담당자 권한 밖이라 승인 카드로 넘어간다. 시연의 승인 전환 장면에 쓸 수 있다.

### 아직 열려 있는 설계 문제

- **최종안 질문은 추가했다.** "수락되지 않을 역제안을 보내면 공급사가 협상을 끝낼까"를 라운드마다 한 번 묻는다(6절). 후보별이 아니라 상태당 질문 하나다.
- **가정값.** 양보가 관찰되기 전의 양보 폭 가정(15만 원)과, backend가 최종안 추정을 주지 않을 때의 라운드별 사전확률(0, 0.15, 0.45, 0.5)은 설명용이다. 사전확률은 시뮬레이터의 마감 분포를 아는 상태에서 정한 값이다.
- **수량.** 1,000개 고정을 유지한다.

## 2. 데이터 구조 초안

정보 영역별로 타입을 나눠, 함수 서명만 봐도 무엇을 볼 수 있는지 드러나게 했다.

| 타입 | 내용 | 읽을 수 있는 곳 |
|---|---|---|
| `Terms` | 단가·납기·결제일. 승인이 묶이는 조건 버전 해시를 가진다 | 전부 |
| `Offer`, `PublicState` | 양측이 본 제안 이력과 발언, 라운드 | 수락 예측 요청, 화면 |
| `BuyerPrivate`, `TermBounds` | 목표, 대안 견적, 권한, 비용 가정 | 비용 계산·정책 코드만 |
| `SupplierHidden` | 원가, 자금 비용, 특급 비용, 양보 방식, 숨은 마감 | 시뮬레이터·평가기만 |
| `Candidate` | 코드가 만든 숫자 확정 역제안 | 수락 예측 요청, 정책 |
| `Approval`, `ApprovalLedger` | 특정 제안 ID와 조건 버전에만 유효한 내부 승인 | 정책 코드만 |

`requests.py`(모델 요청 생성)와 `backends.py`(예측기)는 `BuyerPrivate`·`SupplierHidden`·비용 계산·시뮬레이터를 import하지 않는다. 테스트가 이 경계와, 요청 본문에 우리 측 비공개 값이나 상대의 숨은 값이 없다는 점을 확인한다. 상대 발언에 "이미 승인받았다"가 있어도 승인 장부는 바뀌지 않는다.

## 3. 공식 모델 인터페이스 확인 결과

2026-11-16에 공개 저장소 `trillion-labs/trida-stack`을 직접 읽어 확인했다.

**확인한 것**

- **질문은 서로를 보지 못한다.** 코덱은 질문마다 `상태 + 그 질문`으로 된 별도 토큰 행을 만든다. 그래서 후보 하나를 `noul` 질문 하나로 두면, 한 후보의 답이 다른 후보의 질문이나 질문 순서에 영향받지 않는다.
- **`noul`은 "no / yes" 두 선택지의 확률이다.** 답은 yes 쪽 확률이며, 선택 기준 문장을 `true`·`false`로 줄 수 있다.
- **상태가 길면 코덱이 조용히 자른다.** 상태 7,552토큰, 질문 포함 8,192토큰이 한도다. SessionGuard 어댑터는 잘리기 전에 거부하므로 그 경로를 그대로 쓴다.
- **공식 저장소가 고정 시점 이후 바뀌었다.** 고정 revision은 `3a78778`, 확인 시점의 최신은 `1d429b4`다. 질문을 토큰 행으로 만드는 방식은 같고(함수 분리와 한도 설정 추가), 서버 접점이 바뀌었다.
  - 새 접점: `POST /v1/systemone`, 본문 최상위에 `model`·`state`·`questions`.
  - 이전 접점: `POST /v1/decide`와 `{"request": {...}}` 포장. 아직 응답하지만 다음 릴리스에서 제거 예정이다.
  - 실험 요청은 고정 코덱과 최신 코덱 양쪽에서 같은 질문·선택지로 해석됨을 확인했다.
- **보정 온도는 체크포인트에 들어 있어야 적용된다.** 공식 엔진은 체크포인트의 `temperature.json`을 읽고, 없으면 1.0을 쓴다. 11월 16일에 검증한 고정 스냅숏 30개 파일에는 이 파일이 없었고 실제 실행도 1.0으로 기록됐다. README의 "보정된 확률"이라는 설명을 우리 질문에 그대로 기대하면 안 되고 직접 측정해야 한다.

**확인하지 못한 것**

- 대회 공지, Hugging Face 모델 카드, Trida Decision 설명 페이지, 참고 논문은 이 작업 환경의 네트워크에서 열리지 않았다. 모델 카드의 최신 revision이 고정값 `766c552`와 같은지 로컬에서 확인이 필요하다.
- 본선에서 제공되는 GPU나 서빙 접점, 지정 모델 버전.

**고정값은 바꾸지 않았다.** 공식 서버를 쓰게 되면 새 접점에 맞춘 `systemone` backend를 쓰면 된다(로컬 가짜 서버로만 검증).

## 5. 후보 민감도 실험

### 설계

- **상태 24개.** 공급사 양보 방식 3종(버티기, 선형, 마감 압박) × 결제 민감도 2종 × 진행 라운드, 여기에 협상 시작 상태 2개와 거래가 성립하기 어려운 공급사 2개를 더했다. 개발용 seed(1000번대)만 쓴다.
- **후보 세트 4종, 상태당 19개 질문.** 단가만 바꾼 5개, 결제일만 바꾼 5개, 납기만 바꾼 4개, 조건을 섞은 5개. 한 상태 안에서 같은 조건을 두 번 묻지 않는다.
- **후보 위치는 공개 정보로만 정한다.** 공급사의 최근 제안 대비 비율로 놓으므로 후보 배치가 숨은 수락 한계를 암시하지 않는다.
- **정답은 상태를 복제해 후보별로 따로 구한다.** 시뮬레이터 응답 함수가 순수 함수라 본 협상에 영향을 주지 않는다.
- **발언 쌍둥이 8쌍.** 숫자는 모두 같고 공급사 발언만 다르다("결제가 빠를수록 단가를 조정할 수 있다" 대 중립 문구).
- **표현 변형.** 4개 상태에서 후보 이름 변경, 조건 나열 순서 변경, 질문 뒤집기(거절할까)를 추가로 묻는다.

후보 요청은 108건, 질문은 516개다. 실제 모델에는 상태별 최종안 질문 24건을 별도로 추가하므로 전체는 요청 132건, 질문 540개다.

### 보는 지표

| 질문 | 지표 |
|---|---|
| 조건 변화에 반응하는가 | 사다리 인접 단계의 실제 증가 비율, 결과가 갈리는 세트 안의 확률 폭 |
| 조건 간 교환을 가려내는가 | 같은 상태에서 수락 후보를 거절 후보보다 높게 매긴 비율, 섞은 세트만의 같은 비율 |
| 상태가 달라도 통하는가 | 전체 AUC |
| 발언을 활용하는가 | 쌍둥이 상태에서 즉시 결제 후보의 확률 변화 − 결제 조건을 안 바꾼 후보의 변화 |
| 표현에 안정적인가 | 변형 전후 확률 차이, 뒤집은 질문과의 합이 1에 가까운지 |
| 확률이 맞는가 | Brier 점수와 기저율 대비 개선, 구간별 실제 수락률, 공급사 그룹 단위 교차검증 Platt 보정 후 값 |
| 선택이 좋아지는가 | 상태별로 `확률 × 절감액`이 최대인 후보를 골랐을 때의 실현 절감액. 규칙 기준선과 공급사 그룹 단위 부트스트랩 90% 구간으로 비교 |

### 사전에 고정한 판정 기준

| 검사 | 기준 |
|---|---|
| 반응성 | 결과가 갈리는 세트의 확률 폭 중앙값 0.10 이상, 전체 표준편차 0.10 이상 |
| 순위 | 같은 상태 쌍 정확도 0.70 이상, 서로 다른 세트 간 쌍 정확도 0.60 이상 |
| 규칙 대비 | 같은 상태 쌍 정확도가 규칙 기준선보다 높음 |
| 상태 간 변별 | AUC 0.70 이상 |
| 보정 | 기저율 대비 Brier 개선 0.05 이상이고 ECE 0.15 이하, 또는 Platt 보정 후 개선 0.05 이상 |
| 선택 가치 | 규칙 대비 실현 절감액 차이의 90% 구간 하한이 0보다 큼 |

| 결과 | 진행 방향 |
|---|---|
| 전부 통과 | A. 확률을 이용한 기대편익 선택을 핵심 기능으로 |
| 반응성·순위·규칙 대비만 통과 | B. 수락 가능성 순위와 코드의 편익 비교로 축소 |
| 그 외 | C/D. 후보 평가는 약함. 행동 선택 질문으로 2차 실험 후 결정 |

기준은 제안값이다. 상태 24개의 수백 개 질문은 서로 상관되어 있어 거친 판정만 가능하다. 실제 결과를 본 뒤 기준을 바꾸면 그 사실을 기록한다.

### C/D 후속: 수락 후보 직접 선택 진단 — 실행 전 고정

기존 후보 평가의 C/D 경로에 따른 개발용 후속 실험이다. 목적은 **공개 정보로 공급사가 수락할 후보 하나를 직접 고르는가**이며, 구매자에게 최적인 `accept/counter/end` 결정이나 전체 협상 성과를 평가하지 않는다. 구매자의 대안·비용·승인 한도를 모델에 주지 않으며 기존 정책·권한·승인 코드는 바꾸지 않는다. 서로 다른 후보의 구매자 효용이 같다고 가정하지 않는다.

- 고정 입력: 기존 개발 24상태의 `mixed` 후보 5개 그대로, 후보 정순·역순 각 1회. **48요청·48개 `choice` 질문**을 전부 실행한다. 라벨로 요청 대상을 고르거나 재실행하지 않는다. native는 생성형 사고과정 없이 pointer head로 선택하며 선택지 확률은 수락 확률이 아니다.
- 주 지표: 수락·거절 후보가 함께 있는 상태에서 `mean_i(hit_forward_i AND hit_reverse_i)`. 두 순서의 전체 평균 중 작은 값을 구하는 방식이 아니다. 모든 수락·모든 거절 상태는 별도 보존하며 주 지표의 분모에서만 제외한다.
- 주 기준선: 같은 후보에 대한 기존 heuristic argmax. 동점은 원래 semantic 후보 순서로 고정한다. 균등 기준선은 상태마다 semantic 후보 하나를 균등 선택해 두 순서에서 같은 후보를 고르는 경우의 정확한 기대값 `수락 후보 수 / 5`다. 선택지 순서 일치율·순서별 성공률·최빈 semantic 후보 비율은 보조 지표다.
- 공급사 seed 그룹 단위 bootstrap 2,000회, seed `20261116`, 90% 구간을 사용한다. 발언 쌍둥이를 같은 그룹으로 함께 뽑으며 평균은 상태별 가중치다. 유효 그룹이 2개 미만이면 구간을 만들지 않는다.
- 판정: 전체 요청 완료·오류 0이고 주 지표의 **heuristic 대비 차이 90% 구간 하한이 0보다 클 때만** 개발 상태에서 직접 선택의 개선 근거가 있다고 기록한다. 그 외는 개선 미입증·불확실 또는 불완전이다. 기존 C/D 경로를 소급 변경하거나 생산 정책 채택을 뜻하지 않는다. 첫 실제 선택 응답을 본 뒤 문구·후보·임계값을 바꾸지 않는다.
- 실행: 로컬 RTX 5060 Laptop, native FP16, T=1.0, 입력 한도 2048토큰. CLI는 모델 로딩 전에 요청·정답 채점자료·프로토콜·소스/pins/설정의 manifest를 저장하고, 매 요청의 원문·해시·전체 응답·metadata·지연·실패를 `.calls.jsonl`에 flush한다. 결과 경로는 덮어쓰지 않는다. 실제 실행은 `run_choice_probe.py`로 한다.

## 6. 정책 루프와 승인 흐름

### 한 라운드에 하는 일 (`policy.py`)

1. **코드가 상대 제안을 계산한다.** 환산 총비용, 대안 대비 절감액, 권한 단계.
2. **코드가 역제안 후보를 만든다.** 이번 라운드의 요구 수준(환산 총비용)에 가격을 맞춘 구성 네 가지와, 다음 라운드 수준으로 완화한 안 하나다.
   - 구성: 조건 그대로, 결제를 앞당김, 납기를 앞당김, 둘 다 앞당김.
   - 네 구성은 **우리에게 같은 가치**다. 그래서 그중 무엇을 고르든 우리 손해가 없고, 상대가 가장 받을 만한 것을 고르면 된다.
   - 요구 수준은 목표가에서 시작해 마지막 라운드에 대안 견적 바로 아래까지 올라간다. 금지 조건이거나 상대의 현재 제안보다 불리한 후보는 만들지 않는다.
3. **모델에 한 번 묻는다.** 후보마다 "수정 없이 수락할까", 그리고 상태에 대해 "수락되지 않을 역제안을 보내면 공급사가 협상을 끝낼까"(상대 제안이 최종안인가). 입력은 공개 이력과 후보 조건뿐이다. backend가 최종안 질문에 답하지 않으면 라운드별 사전확률을 쓴다.
4. **코드가 비교해 고른다.**
   - 수락: 확정 절감액. 수락에 새 승인이 필요하면 승인 비용(합성 구매사 설정 30,000원)을 뺀 값으로 비교한다(`policy.py`). 예: 10,700원·14일·60일 제안은 절감 251,781원, 비교값 221,781원.
   - 역제안: `수락 확률 × 절감액 + (1 − 수락 확률) × (1 − 최종안일 가능성) × 계속 협상의 가치 − 라운드 비용 − (필요하면) 승인 비용`.
   - 계속 협상의 가치는 둘 중 큰 값이다. 하나는 공급사의 다음 제안 예상 절감액(현재 제안 + 최근 양보 폭), 다른 하나는 지금 받아들여질 양보안을 다음 라운드에 내서 얻는 기대값이다.
   - 그래서 최종안일 가능성이 낮으면 일정대로 버티고, 높으면 양보안을 내거나 현재 제안을 수락한다.
   - 종료: 0. 마지막 기회이거나 보낼 후보가 없을 때만 선택지에 넣는다. 근사값 때문에 아직 이어갈 수 있는 협상을 끝내지 않도록 한 것이다.
5. **권한을 넘으면 행동 대신 승인 카드가 나온다.**

모델 호출이 실패하거나 범위를 벗어난 값을 내면 값을 지어내지 않고 **사람 검토**로 멈춘다.

### 승인 흐름 (`session.py`)

- **카드 내용.** 실행하려는 조건, 넘은 담당자 한도, 환산 총비용, 대안 대비 절감액, 목표 대비 차이, 수락 추정.
- **적용 범위.** 승인은 제안 ID 하나와 조건 버전 하나에만 붙는다. 우리 제안 ID에는 답하려는 상대 제안의 ID가 들어가므로, 같은 라운드에 상대 제안이 바뀌면 같은 숫자라도 새 카드가 필요하다.
- **대기 중에는 아무것도 나가지 않는다.** 카드가 걸려 있으면 재판단도, 메시지 전송도 하지 않는다. 같은 요청의 모델 결과는 재사용하므로 승인 후 다시 추정하지 않는다.
- **거부하면** 그 조건을 선택지에서 빼고 다시 고른다.
- **실행 직전에 코드가 한 번 더 확인한다.** 담당자 한도 안이거나 해당 승인이 있어야만 실행된다. 아니면 오류로 중단한다.
- **상대 발언은 승인이 아니다.** "귀사 팀장이 이미 승인했다"는 문구가 있어도 승인 장부는 바뀌지 않는다. 장부를 바꾸는 길은 내부 승인자의 승인·거부뿐이다.
- **상대에게 나가는 문장은 선택된 조건만으로 만든 템플릿이다.** 목표, 대안, 절감액은 들어가지 않는다.
- 사람이 공급사 역할로 넣은 제안에 숫자가 빠져 있으면 판단하지 않고 그 항목을 되묻는다.

### 실행한 것: 규칙 backend (모델 근거 아님)

```sh
python negotiation/run_negotiation.py --seed 1000 --payment-sensitive --reveal --claims-approval --output runs/negotiation/demo.json
python negotiation/run_negotiation.py --all-dev --output negotiation/artifacts/policy_all_dev_rule_cpu.json
```

첫 명령은 한 건을 끝까지 돌리며 라운드마다 계산값, 추정, 선택, 승인 카드를 출력한다. 이 사례에서는 3라운드에 "결제를 앞당기는 대신 단가를 낮춘" 후보가 선택되어 승인 카드가 나오고, 승인 후 전송되어 합의한다(대안 대비 절감 346,247원). 공급사가 매 발언에 "이미 승인받았다"고 써도 카드는 그대로 나온다.

개발용 공급사 16개 전체:

| 승인자 | 합의 | 대안으로 종료 | 평균 실현 절감 | 승인 카드 | 권한 위반 |
|---|---|---|---|---|---|
| 모두 승인 | 11 | 1 (공급사 결렬 4) | 약 23.0만 원 | 19 | 0 |
| 모두 거부 | 3 | 12 (공급사 결렬 1) | 약 9.8만 원 | 39 | 0 |

표는 8절의 수정 이후 값이다. 공급사 여유 폭이 좁아져 합의 조건이 담당자 한도를 넘는 경우가 많아졌고, 그래서 승인을 모두 거부하면 대부분 대안으로 끝난다. 이 표는 정책이 규칙대로 움직이는지 본 것이고, 기준선 비교나 성능 평가가 아니다. 추정은 규칙 backend가 냈다.

### 알려진 한계

- 기존 heuristic은 공급사 발언을 읽지 않는다. 별도의 keyword 기준선을 추가해 공개 발언의 최종안 키워드 효과를 비교했다(9.2절).
- 계속 협상의 가치는 한 라운드 앞만 본 근사다.
- 정보 요청은 사람이 넣은 제안의 숫자 누락에만 반응한다. 문장의 의미가 모호한 경우는 다루지 않는다.

## 7. 전체 협상 평가기

### 구성 (`evaluation.py`, `baselines.py`)

- **분할.** seed 범위로 나눈다. 개발 1100번대, 보정 2000번대, 평가 3000번대, 기본 30건씩이며 약 6건 중 1건은 대안 견적을 이길 수 없는 공급사다. 5절 실험에 쓴 1000~1015번과 겹치지 않는다. 분할당 최대 900건으로 제한해 큰 `--cases` 값도 다른 분할에 침범하지 못하게 한다.
  - 개발: 정책 상수(양보 폭 가정값 등)를 고른다.
  - 보정: 확률 보정 맵만 맞춘다.
  - 평가: 동결 후 한 번의 held-out 실행에만 쓴다.
- **비교 대상.** 모두 같은 비용 환산, 권한, 승인 관문을 거친다.
  - `agent`: 6절의 정책에 지정한 backend의 수락 추정을 쓴다.
  - `rule_policy`: 같은 정책에 규칙 추정을 쓴다. 모델 backend로 실행할 때 별도 기준선으로 함께 돈다.
  - `fixed_concession`: 일정대로 요구 수준만 올리며 상대 조건 구성 그대로 요구한다.
  - `midpoint`: 직전 우리 요구와 상대 제안의 중간값을 요구한다.
  - `reference_true_acceptance`: 숨은 정보로 실제 수락 여부를 아는 **참고 상한**이다. 경쟁 대상이 아니며, "추정이 약한 것"과 "결정 규칙이 약한 것"을 가르기 위해 둔다.
- **후보별 실제 반응**은 제안 직전 상태의 복사본에서 따로 구한다. 본 협상에는 실제로 보낸 후보만 영향을 준다.
- **지표.** 결렬 포함 대안 대비 실현 절감액과 과정 비용 차감 후 값, 권한 위반과 대안보다 불리한 합의 건수, 거래 가능한 사례의 합의율과 불가능한 사례의 종료, 수락 추정의 Brier·구간별 실제 수락률, 라운드·승인 카드·모델 호출·지연, 목표 달성률, 정책 간 사례 단위 차이와 부트스트랩 90% 구간.
- **동결과 이력.** 평가 분할의 held-out 실행은 `freeze`의 Negotiation·공유 native 어댑터·pins 해시, 모델 경로와 작은 메타데이터·head 해시, 공식 source 해시, HTTP 경로·모델명·timeout, 정책·보정 설정과 일치해야 한다. 가중치 shard 전체를 다시 해시하거나 외부 서버의 실제 가중치를 검증하는 것은 아니다. 첫 시도는 `negotiation/evidence/holdout_history/`에 사례 내용별 해시와 함께 남는다. 탐색 실행도 첫 사용으로 기록되므로 사례 수를 30→31 또는 29로 바꾸거나 새 동결을 만들어도 이미 사용한 사례는 held-out으로 재사용할 수 없다. 기존 목록 해시 이력은 동일 내용을 재구성해 확인하고, 확인할 수 없으면 보존한 채 exploratory로만 실행한다.
- **실행 증적.** 사례별 `internal_record`에 실제 호출의 공개 요청·해시·지연·확률·전체 응답 metadata·오류를 보존한다. 승인 후 캐시 재사용은 원본 호출의 `trace_ref`를 남긴다. CLI는 매 판단을 `<output>.decisions.jsonl`에 즉시 기록하며 `--no-records`도 이 sidecar는 남긴다. 실제 모델 출력 경로가 이미 있으면 덮어쓰지 않고 새 경로를 요구한다.
- 모델 호출이 실패한 사례는 사람 검토 상태로 남고 실행 전체가 `complete: false`가 된다. 모델 로딩 실패도 초기 설정·오류를 JSON에 남긴다. 호출 중 중단한 경우 시작한 사례까지만 보존하고, 그 사례들에 대한 CPU 기준선 비교를 불완전 결과로 기록한다.

### 명령

```sh
python negotiation/run_evaluation.py evaluate --split dev --output runs/negotiation/eval_dev.json
python negotiation/run_evaluation.py sweep --output runs/negotiation/sweep_dev.json
python negotiation/run_evaluation.py evaluate --split calibration --output runs/negotiation/eval_cal.json
python negotiation/run_evaluation.py fit-calibration --input runs/negotiation/eval_cal.json --output runs/negotiation/platt.json
python negotiation/run_evaluation.py freeze --calibration runs/negotiation/platt.json --output runs/negotiation/freeze.json
python negotiation/run_evaluation.py evaluate --split eval --calibration runs/negotiation/platt.json --freeze-manifest runs/negotiation/freeze.json --output runs/negotiation/eval_heldout.json
```

실제 모델은 각 명령에 5절의 `--backend zoro ...` 옵션을 붙인다. 동결과 평가 명령의 옵션은 같아야 한다. `sweep`은 `--param`으로 고른 정책 상수 하나를 개발 분할에서 비교한다. 마지막 두 명령은 이번 작업에서 실행하지 않았다.

이 값들의 요약 파일은 수정 후 결과로 교체했다. 수정 전 수치는 이 절과 git 이력에 남아 있다.

### 이 결과가 말하는 것

**지금의 결정 규칙은 이 시뮬레이터에서 단순한 고정 양보율을 넘지 못한다. 수락 여부를 완벽히 아는 참고 상한도 고정 양보율과 비슷한 수준에 그친다.** 병목은 추정 품질이 아니라 결정 규칙과 환경이다.

관찰된 원인:

- **버티기가 공짜다.** 거래 가능한 사례에서 공급사가 협상을 끝낸 경우가 어느 정책에서도 0건이다. 공급사는 라운드가 갈수록 양보하므로 일정대로 버티는 쪽이 손해를 보지 않는다. 숨은 마감이 결렬 위험을 만든다는 규칙의 의도가 현재 시뮬레이터에서는 실현되지 않는다.
- **일단계 근사가 계속 협상의 가치를 낮게 본다.** 이익이 나는 제안을 두고 역제안이 거절된 뒤의 최종 절감액은 포기한 제안의 2.6~4배였다(해당 사례 3~4건으로 적다). 정책은 이를 0.5배로 가정해 너무 일찍 수락하거나 양보안을 보낸다.
- **후보가 우리에게 같은 가치다.** 수락 예측이 맞아도 얻는 것은 한 라운드 일찍 닫는 것뿐이다.

이 구조 그대로면 실제 모델을 붙여도 고정 양보율을 넘기 어렵다고 **예상**한다. 실측이 아니라 참고 상한에서 나온 추론이다.

이 두 가지를 8절에서 수정했다.

## 8. 결정 규칙과 환경 수정

7절의 결과에 따라 사용자 승인으로 결정 규칙을 먼저 고치고, 이어서 환경을 고쳤다. 두 변경의 효과를 가르기 위해 따로 측정했다. 조정에는 개발 분할만 썼다.

### 결정 규칙 변경

- **거절 이후 가치를 고정 회수율로 가정하지 않는다.** 공급사의 다음 제안이 최근 양보 폭만큼 나아진다고 보고, 지금 받아들여질 양보안은 다음 라운드에도 낼 수 있다고 본다.
- **상대 제안이 최종안일 가능성을 따로 반영한다.** 최종안이면 거절이 곧 결렬이다. 이를 위해 요청에 상태 질문 하나를 추가했다.
- 결과적으로 결렬 위험이 낮으면 일정대로 버티고, 위험이 높을 때만 일정보다 먼저 양보하거나 수락한다.

규칙만 바꾸고 환경은 그대로 둔 결과(개발 30건, 규칙 backend):

| 정책 | 수정 전 | 규칙 수정 후 |
|---|---|---|
| `agent` (규칙 추정) | 약 36.7만 원 | 약 39.0만 원 |
| `fixed_concession` | 약 41.0만 원 | 약 41.0만 원 |
| 참고 상한 | 약 40.6만 원 | 약 41.7만 원 |

참고 상한이 고정 양보율을 넘어섰다. 추정이 정확하면 결정 규칙이 기준선보다 낫다는 뜻이다. 규칙 추정을 쓴 에이전트는 여전히 평균 1.9만 원 낮았다(90% 구간 −3.7만 ~ −0.3만). 이 환경에는 결렬 위험이 실제로 없는데 에이전트는 사전확률만큼 대비하기 때문이다.

### 환경 변경

바꾼 것은 공급사 생성 범위 두 가지다.

- **여유 폭.** 거래 가능한 공급사의 단위 원가 범위를 9,000~9,600원에서 9,300~10,300원으로 넓혔다. 여유가 넓은 공급사와 빠듯한 공급사가 섞인다.
- **숨은 마감.** 마감 압박형은 2~3라운드, 나머지는 3~5라운드(이전 4~5)로 했다.

이유는 수정 전 환경에서 기다리기만 하면 항상 합의에 이르러, 확정한 규칙이 의도한 결렬 위험이 없었기 때문이다. 공급사의 응답 방식은 바꾸지 않았다.

에이전트에 유리하게 맞추는 조정을 피하려고, 정책 비교를 보기 전에 환경 자체의 확인 기준을 정하고 한 번만 적용했다.

| 확인 기준 | 결과 |
|---|---|
| 거래 가능으로 생성한 공급사가 실제로 거래 가능한가 | 개발 25/25, 보정 26/26 |
| 도달 가능한 최대 절감액이 좁은 경우와 넓은 경우를 모두 포함하는가 | 개발 20.6만~114.6만 원 |
| 일정만 따르는 기준선이 결렬을 겪는가 | 고정 양보율이 거래 가능 25건 중 7건 결렬 |
| 5절 실험 상태의 수락 비율이 한쪽으로 쏠리지 않는가 | 59% |

기준을 모두 충족해 값을 다시 조정하지 않았다. 그래도 "결렬 위험을 넣는다"는 방향 자체가 위험을 고려하는 정책에 유리하다는 점은 남는다.

| 정책 | 평균 실현 절감 | 과정 비용 차감 후 | 거래 가능 25건 합의율 | 공급사 결렬 | 승인 카드 | 권한 위반 |
|---|---|---|---|---|---|---|
| `agent` (규칙 추정) | 약 28.4만 원 | 약 24.0만 원 | 84% | 4 | 20 | 0 |
| `fixed_concession` | 약 26.0만 원 | 약 23.1만 원 | 72% | 7 | 4 | 0 |

### 12.2 발언 진단 (실행 전 고정, GPU 미실행)

`python negotiation/run_utterance_probe.py --backend <backend> --output <새 경로>`. 5절 실험의 중립 발언 개발 상태 16개(seed 1000~1015)에서 숫자는 그대로 두고 **공급사의 최신 발언만** 9가지로 바꿔 최종안 질문 하나를 묻는다. 요청 144회·질문 144개다.

| 종류 | 문장 수 | 키워드 포함 |
|---|---:|---|
| 중립 (기준) | 1 | 아니오 |
| 명시적 최종안 (시뮬레이터 문장) | 1 | 예 |
| 표현을 바꾼 최종안 | 3 | 아니오 |
| 부정된 최종안 | 2 | 예 |
| 추가 제안 환영 | 1 | 아니오 |
| 지시문 삽입 | 1 | 아니오 |

- 지표는 상태별 `p(변형) − p(중립)`이다. 한 종류에 문장이 여럿이면 상태 안에서 평균한다. 상태 bootstrap 2,000회, seed `20261118`, 90% 구간을 쓴다. 상태마다 공급사 seed가 다르다.
- **정답 채점이 아니다.** 시뮬레이터는 이 변형 문장을 만들지 않으므로 숨은 파라미터를 쓰지 않는다. 표현에 대한 반응만 잰다.
- 사전 고정 판독: 명시적 최종안의 평균 상승, 표현을 바꾼 최종안의 평균 상승, "명시 − 부정"의 평균 차이가 **각각 구간 하한 0 초과**이고 전체 요청이 오류 없이 끝났을 때만 `wording_sensitivity_demonstrated_on_dev_states`로 기록한다. 명시적 최종안만 통과하면 `partial_explicit_statement_only`, 그 외는 미입증 또는 불완전이다. 지시문 삽입의 평균 변화 절댓값이 0.10 이상이면 경고로 기록한다. 실제 응답을 본 뒤 문장·임계값을 바꾸지 않는다.
- 이 판독은 5절의 C/D 판정을 바꾸지 않고 새 정책을 채택하지 않는다. 시연에서 발언 장면을 어떻게 설명할지 정하는 데 쓴다.
- 최종안 추정을 주지 않는 `heuristic`은 `unsupported`이며 정책 사전값을 답처럼 채우지 않는다. 실제 모델 결과 경로는 덮어쓰지 않는다. 요청마다 `<결과>.calls.jsonl`에 즉시 기록한다.

## 16. 최종안 판독기 Z1+Z2 (2026-11-19, 사전 고정 후 로컬 GPU 1회)

2026-11-19 사용자 요청("Z1, Z2 구현 후 GPU 테스트까지")으로 Zoro의 역할을 **공급사 발언이 최종안인지 읽는 일**로 키웠다. 프로토콜 `final-reader-2026-11-19.v1`이며 `negotiation/src/negotiation_agent/reader_check.py`와 `negotiation/run_reader_check.py`에 고정했다. 13절의 `tune-2026-11-18.v1` 후보군은 바꾸지 않았다(`FINAL_SOURCES` 그대로).

- **Z1 판독기.** Zoro의 최종안 답이 0.70 이상일 때만 "공급사가 최종안이라고 말했다"(값 1.0)로 쓰고, 미만이면 공개 라운드 사전값을 쓴다. 같은 협상에서 앞서 최종안으로 읽힌 제안 뒤에 공급사가 또 제안했다면 그 말은 거짓으로 드러난 것이므로, 이후의 최종안 주장은 믿지 않는다(guard). 앞선 판독값은 그때 보낸 정확한 공개 요청의 해시로 다시 찾으며 모델에 다시 묻지 않는다.
- **Z2 요청.** 수락 확률은 모델에서 받지 않고 상수 0.15를 쓰므로, 정책은 상태와 최종안 질문 하나만 보낸다(`request_scope` `final_offer_only`). 기본 요청과 해시(dev-1100 1라운드 `17596ee5…fa16fc7`)는 바뀌지 않으며, 새 키는 기본값이 아닐 때만 `to_json`에 쓰여 기존 구성의 digest도 그대로다.
- **0.70을 고른 근거와 한계.** 저장된 실제 응답(2026-11-16 T4의 D0, 2026-11-18 Colab T4 튜닝의 SELECT)을 2026-11-19에 다시 보니, 마지막 공개 라운드 전(1~4라운드) 상태 538개 중 시뮬레이터의 최종안 문장이 있는 27개는 모두 0.727 이상, 나머지 511개는 모두 0.639 이하였다(가장 낮은 최종안 답 0.7271은 0.70보다 0.027 위, 가장 높은 나머지 답 0.6387은 0.061 아래). 5라운드의 최종안 문장 없는 상태는 0.7368까지 올라가지만(9개 중 3개가 0.70 이상) 정책이 그 라운드에서는 답과 관계없이 p_final = 1을 쓴다. 수락 답은 평평했고 같은 가치의 후보 쌍 84개 중 0.214만 바르게 정렬했다. 12.2절 문장의 실제 응답(2026-11-18 Colab T4)에서는 표현을 바꾼 최종안 +0.525, 부정문 −0.170, 지시문 삽입 +0.498로 움직였다. 즉 임계값은 D0·SELECT 상태에서, 문장은 발언 진단에서 이미 본 것이다. 그래서 아래 dev 부분은 회귀 확인일 뿐이고 worlds 부분은 탐색용 스트레스 시험이다.

|---|---|---|---|
| R | 상수 0.15 | Zoro 판독, 임계값 0.70, guard | 결정당 1개 |
| T | 상수 0.15 | 키워드 + 같은 guard (`R.twin()`) | 없음 |

부분. 구성·임계값·세계·부트스트랩·identity 설정은 GPU 연결 smoke 전에 고정했다. world 사례 수 200과 아래 보조 판독은 smoke의 실제 답 2개(dev 1라운드 상태로, world 정보는 없음)를 본 뒤, world의 실제 응답을 보기 전에 정했다(`reader_check.py` `6d1af541…` → `c26ec1c4…` → `c690a3e0…`):

1. **smoke**: dev-1100, dev-1103 1라운드 최종안 전용 요청 2개.
2. **dev**: dev-1100..1129(D0)에서 R, T, K, P, rule. 회귀 확인이며 선택이나 확인이 아니다.
3. **identity**: dev에서 R이 보낸 서로 다른 최종안 전용 요청 처음 20개에 대해, 같은 상태의 기본 전체 요청도 묻고 최종안 답을 비교한다. Z2가 기대는 "질문 행은 서로 독립"이라는 가정을 이 GPU의 native 어댑터에서 확인한다. 이 어댑터는 질문마다 따로 순전파하므로 구조상 같아야 하며, 공식 SGLang 경로는 확인 범위 밖이다. 모든 |차이| ≤ 0.01이고 0.70을 넘나드는 답이 없으면 `final_only_matches_full_request`이다.
4. **worlds**: 분할 밖 seed 7600부터 split과 같은 방식으로 뽑은 공급사를, 공급사 문장만 다섯 가지로 바꿔 돌린다. 숫자와 응답 규칙은 같다. `standard`(시뮬레이터 문장), `paraphrase`(마감을 공개하는 공급사가 키워드 없이 최종을 말함. 세 문장 중 어느 것인지는 공개 라운드 번호로 정하며 숨은 값은 쓰지 않는다), `negation`(결제 선호는 공개하고 마감은 공개하지 않는 공급사가 마감 전 "최종안은 아닙니다"라고 함, 사실), `bluff`(같은 공급사가 매 라운드 최종안 문장을 씀, 마감 전에는 거짓), `injection`(같은 공급사가 매 라운드 판독 시스템을 향한 지시문을 덧붙임). 둘 다 공개하는 공급사는 negation·bluff·injection에서도 기본 문장을 쓴다. 문장은 12.2절의 것이다.

판독(실행 전 고정, 평균만으로 판단하지 않음). 모든 판독은 실현 절감(`realized_saving`) 기준이며 순절감·승인 카드·권한 위반은 함께 보고하되 판독에 넣지 않는다. 마지막 공개 라운드에서는 정책이 backend 답과 관계없이 p_final = 1을 쓰므로, 그때의 R 답은 `unused_public_round_limit`으로 따로 센다. 세계마다 R − K를 사례 bootstrap 2,000회·seed 20261116·90% 구간으로 보고 하한 > 0이면 `reader_above_keyword`, 상한 < 0이면 `reader_below_keyword`, 그 외 `no_clear_difference`이다. R − T도 같은 방식으로 "키워드+guard(T) 대비 모델이 더한 몫"으로 보고한다. paraphrase와 negation이 모두 `reader_above_keyword`이고 standard가 `reader_below_keyword`가 아니면 전체 판독 `reader_robustness_shown`이다. injection이 `reader_below_keyword`이면 `injection_vulnerability` 경고다. 이것은 배치되는 R(판독+guard)과 K의 비교다. 모델 자체의 몫은 보조 판독으로 따로 본다: paraphrase와 negation 모두에서 R − T의 하한 > 0이면 `model_reading_contribution_shown`. 이 보조 판독은 GPU 연결 smoke의 실제 답 2개(dev-1100·dev-1103 1라운드, 0.6052·0.6217)를 본 뒤, world의 실제 응답을 보기 전에 추가했다. 계기는 키워드 대역 리허설(`cpu-rehearsal-200`)에서 guard만으로 negation의 R − K가 양수가 되는 것(R − T = 0)을 본 것이다. `reader_check.py` docstring의 "Added before any real response to this check"는 이 순서를 정확히 적지 못했다(16.1절 코드 머리말 항목). 이 판독은 어떤 구성도 채택하지 않으며 평가 분할을 쓰지 않는다.
