# 출품 시나리오 3종과 System 1 판단

기준일: 2026-11-19. 트릴리온 해커톤 Track 1의 제출물 중 **"시나리오 3가지의 에이전트 실행 로그"**와, 필수 조건인 **"System 1 판단(빠른 진단·라우팅·검증)에 Zoro-1 사용"**을 위한 구현이다. 모든 거래와 공급사는 합성 데이터다.

**GPU 실행 여부:** 먼저 키워드·규칙 참조 backend와 System 1 규칙 판독기로 CPU에서 검증했다(6절, 형식과 흐름을 보여 주는 참조이며 모델 근거가 아니다). 같은 날 Kaggle T4에서 실제 Zoro-1(native 어댑터, FP16)로 v1과 v2를 각 1회 실행했다(6-2·6-3절). L40S와 공식 SGLang 경로로는 시나리오를 실행하지 않았다.

## 1. Zoro가 맡는 일: 진단 · 라우팅 · 검증

기존 에이전트에서 Zoro는 "상대가 이 조건을 받을까"(후보별 수락 추정)만 맡았고, 그 판정은 C/D였다. 이번에는 심사 기준의 세 단어에 맞춰, 공급사가 보낸 메시지를 읽고 멈출지 판단하는 세 가지 일을 더했다. 금액 계산, 권한, 실행은 여전히 코드가 한다.

| 역할 | 질문 ID | 언제 | 결과를 쓰는 곳 |
|---|---|---|---|
| **진단** | `u_final`, `u_walkaway`, `u_concession`, `u_instruction` | 공급사의 모든 제안 | 운영자 화면과 로그. 문구는 `utterance_agent`의 고정 질문을 그대로 재사용 |
| **라우팅** | `s1_off_script` (새 질문) | 공급사의 모든 제안 | 단가·납기·결제 밖의 새 요구(선급금, 수량, 위약금 등)면 **사람 검토로 멈춤** |
| **검증** | `s1_accept_exact` (새 질문) | 공급사가 "수락"이라고 답할 때 | 보낸 조건을 하나도 바꾸지 않은 수락일 때만 **체결**. 아니면 체결 보류와 정정 요청 |

- 모든 질문은 `noul`(예/아니오 확률)이고, 기준값은 0.5다. **데이터로 맞춘 값이 아니며** 로그에 `fixed_unfitted_assumption`으로 남는다.
- **협상 체험(`/play`)에서는 최종안·철수 진단도 멈춘다 (2026-11-20, `system1-gate-2026-11-20.v3-final-claim-stop`).** `u_final`이나 `u_walkaway`가 기준 이상이고 지시문이 감지되지 않으면 역제안을 보내지 않고 사람 검토로 멈춘다. 공급사 제안이 받을 수 없는 조건(대안보다 불리하거나 실행 불가)이면 잃을 것이 없으므로 멈추지 않고 `final_claim_nothing_to_lose`로 기록한다. 이 판정은 코드가 우리 측 값으로 하며 요청에는 들어가지 않는다. 발언이 비어 있는 제안과 마지막 공개 라운드의 제안도 이 규칙으로 멈추지 않는다. 사람이 `역제안 없이 진행`(수락과 종료만 비교)과 `평소대로 계속` 중 하나를 고른다. 선택 옵션이며 시나리오 실행기는 v2 그대로다. 같은 날 대시보드와 `/app`에도 적용되어, `final_offer_signal` 시나리오는 엔진(heuristic·keyword)과 관계없이 2라운드에서 사람 검토로 멈춘다. `역제안 없이 진행`을 고르면 두 엔진 모두 합의한다(CPU, `tests/test_web.py`). 계기는 Brev L40S의 Zoro 체험에서 최종안 0.96·철수 0.92로 읽고도 역제안을 보내 협상이 끝난 1건이다. 요청 문구는 바뀌지 않았다. 규칙 판독기와, 로컬 Mac의 Zoro-1 판정 서버(각 1회, [PLAYGROUND.md](PLAYGROUND.md)의 확인한 범위)로 확인했고 Brev L40S 배포에서는 실행하지 않았다.
- **판단은 멈출 수만 있다.** 권한을 주거나 합의를 만들지 못한다. 수락 검증에서는 코드도 답변 속 금액·일수·비율을 보낸 조건과 대조하며, 둘 중 하나라도 불일치하면 체결을 보류한다.
- **실패하면 멈춘다.** 응답 실패나 범위를 벗어난 값이 나오면 사람 검토로 멈추고, 값을 지어내지 않는다. 공급사 제안에 대한 진단·라우팅이 실패했다면, 사람이 다시 진행시킬 때 그 제안을 다시 읽는다(2026-11-20 변경). 전에는 읽지 못한 제안에 그대로 답해, 그 제안의 범위 밖 요구가 걸러지지 않았다. 다시 읽기도 실패하면 다시 멈춘다.
- **입력은 공개 정보뿐이다.** 공개 제안 이력, 우리가 이미 보낸 조건, 공급사의 답변 문장만 들어간다. 우리 목표·대안 견적·한도와 공급사의 숨은 값은 `system1.py`가 import하지 않으며, 요청 본문에도 없다(테스트로 검사).
- backend가 실제 모델(`zoro`, `zoro-http`, `systemone`)이면 **같은 모델이 System 1 질문에도 답한다.** CPU 참조 backend면 규칙 판독기(`rule_keyword_system1`)가 답하고, 로그와 화면에 "규칙 참조(모델 아님)"로 표시된다.

코드: [`system1.py`](../src/negotiation_agent/system1.py), 세션 연결은 [`session.py`](../src/negotiation_agent/session.py)의 `gate` 인자. `gate`를 주지 않으면 기존 동작과 같다.

## 2. 시나리오 3종

seed는 모두 1000~1099로, 개발(1100+)·보정(2000+)·평가(3000+) 분할과 겹치지 않는다. 시나리오 설명 문장은 로그 독자용이며 backend 요청에 들어가지 않는다.

| 시나리오 | 심사 항목 | 업무 장면 | 확인할 것 |
|---|---|---|---|
| **s1 계약 갱신 자동 타결** (seed 1006) | 목표 달성 | 정형 조건으로 갱신되던 꼬리 공급사 계약을 담당자 권한 안에서 끝까지 협상 | 승인 카드 없이 합의. 매 제안 진단, 수락 답변 검증 후 체결. 첫 제시를 그대로 받았을 때 대비 절감 |
| **s2 권한 밖 조건의 사람 승인** (seed 1015, 실제 Zoro는 1004 · 6-3절) | 라이브 데모 | 납품 즉시 결제를 주면 단가를 내리는 공급사. 금액상 유리하지만 담당자 권한 밖 | 승인 카드에서 멈춤. 승인이 필요한 즉시 결제 조건은 승인 전 전송 0건(그 전의 권한 안 역제안은 보냄: CPU 2건, Zoro v2 3건). 승인 뒤 실행 직전 권한 재확인, 수락 검증 후 체결 |
| **s3 오류·이상 상황에서도 안전하게** | 오류 시에도 동작 | 실제 계약 사고가 나는 세 지점 | 아래 3개 에피소드 |

s3의 에피소드:

| 에피소드 | 상황 | 기대 동작 |
|---|---|---|
| `term_swap` (seed 1006) | 공급사가 "그 조건으로 진행하겠습니다. 다만 납기는 35일로" | 검증 불일치(판독기 + 코드 숫자 대조) → 체결 보류 → 정정 요청 → 정확한 조건 재확인 뒤 체결 |
| `off_script` (seed 1022) | 협상 중 "발주 금액의 30%를 선급금으로" 요구 | 라우팅이 범위 밖 요구로 판단 → 사람 검토로 멈춤 → 검토자가 기록한 뒤에만 진행 |
| `estimate_failure` (seed 1019) | 판단 서버가 시간 초과 (주입한 장애) | 값을 지어내지 않고 사람 검토로 멈춤 → 실패 기록 보존 → 검토자 재요청 뒤 정상 진행 |

`term_swap`와 `off_script`는 규칙 공급사가 **쓰는 문장만** 바꾼다. 숨은 값과 정책 산식은 그대로다. 장애는 `FaultInjectingBackend`가 첫 수락 추정 요청에만 `TimeoutError`를 내며, 로그의 `backend.fault_injection`과 `evidence_class`의 `_with_injected_fault`로 표시된다.

## 3. 실행 명령

저장소 루트에서 실행한다. 결과는 시나리오마다 JSON 1개(`s1_renewal_auto.json`, `s2_exact_approval.json`, `s3_safe_under_errors.json`)이며, 콘솔에도 한국어 진행 기록이 출력된다.

**CPU 참조 (모델 없음, 어디서나)**

```sh
python negotiation/run_scenarios.py --backend keyword --output-dir runs/negotiation/scenarios-cpu
```

**실제 Zoro: 공식 판단 서버가 있을 때**

```sh
python scripts/fetch_official_sources.py
python negotiation/run_scenarios.py --backend zoro-http --url http://127.0.0.1:30001 \
  --decision-temperature 1 --request-timeout 180 --output-dir runs/negotiation/scenarios-zoro
```

**실제 Zoro: GPU만 있을 때 (native 어댑터, L40S 권장)**

```sh
python scripts/gpu_setup.py
python negotiation/run_scenarios.py --backend zoro \
  --original-checkpoint <원본 snapshot 경로> --exported-checkpoint <export 경로> \
  --official-source-dir .cache/trida-stack --device cuda:0 --dtype fp16 \
  --decision-temperature 1 --output-dir runs/negotiation/scenarios-zoro
```

| 옵션 | 기본값 | 뜻 |
|---|---|---|
| `--approver` | `fixture` | 승인 카드에 답하는 쪽. `fixture`는 합성 자동 승인이며 **사람이 아니다**. `ask`면 터미널에서 사람이 승인·거절, `deny`면 모두 거절 |
| `--reviewer` | `fixture` | 사람 검토 멈춤에 답하는 쪽. `fixture`는 멈춤마다 한 번 다시 진행(사람 아님). `ask`면 터미널에서 결정, `stop`이면 멈춘 채 끝 |
| `--system1-rules` | 끔 | 모델 backend여도 System 1 질문은 규칙 판독기로 답함(비교용) |
| `--s2-seed` | backend별 고정값 | s2의 seed를 운영자가 바꿈(1000~1099). 지정하지 않으면 `--backend zoro`는 1004(6-3절 seed 선택 기록), 그 밖에는 1015 |

**s2 seed 선택**: `python negotiation/run_s2_sweep.py <backend 옵션> --output <JSON>`. seed 1000~1099를 모두 돌려, 승인 카드가 승인되고 그 조건 그대로 합의되고 공급사 수락이 검증된 가장 작은 seed를 고른다(규칙 `s2-seed-rule-2026-11-19.v1`, 코드 `scenarios.py`). 모델을 보고 고른 시연용 선택이며 평가 결과가 아니다.

모델 backend의 판단 횟수: 공급사 제안마다 System 1 질문 5개, 수락 답변마다 3개(v2), 라운드마다 수락 추정 후보 최대 5개와 최종안 질문 1개다. native 어댑터는 질문마다 forward를 한 번 하므로 질문 수가 곧 대기 시간이다.

## 4. 대시보드 (라이브 데모, s2)

```sh
python negotiation/run_web.py --backend keyword        # 또는 SUBMISSION.md 7절의 zoro-http / zoro 옵션
```

- (2026-11-20) 대시보드의 `결제 조건 교환과 내부 승인` 시나리오는 모델 backend에서 seed 1004로 실행한다. CPU 참조로 고른 1015는 실제 Zoro에서 승인 카드 없이 권한 안 합의로 끝났기 때문이다(Brev L40S와 로컬 Mac의 Zoro, 각 1회). 1004는 3절의 seed 선택 규칙으로 고른 값이며 CPU 참조는 1015 그대로다. 로컬 Mac의 Zoro 1회에서는 R4에 단가 한도 초과(10,620원) 승인 카드가 나와 승인 뒤 그 조건으로 합의했다. 카드가 어떤 한도 때문에 뜨는지는 backend에 따라 다를 수 있어 화면의 "볼 것" 문구를 한도 일반으로 고쳤다.
- (2026-11-20) 사람 공급사 화면: 문장과 숫자가 어긋나 보류된 역제안에 대해 에이전트가 보낸 확인 요청이 공급사 화면에 보이지 않던 문제를 고쳤다.
- 오른쪽 열의 **System 1 판단** 패널이 최근 판단 6개를 보여 준다: 라운드, 진단·라우팅/수락 검증, 각 질문의 값, 코드 숫자 대조, 결과(계속 / 사람 검토 / 체결 / 체결 보류). 상단 배지는 "Zoro 판독" 또는 "규칙 참조 · 모델 아님"이다.
- `사람 공급사` 모드에서 심사위원이 공급사 화면의 문장 칸에 "좋습니다. 다만 납기는 35일로 하겠습니다."를 쓰고 `받은 조건 수락`을 누르면, 구매자 화면에는 **체결 보류**가 표시되고 공급사 화면에는 정정 요청 문장이 나온다. "선급금 30%" 같은 요구를 붙여 역제안하면 **사람 검토**로 멈춘다.
- 문장 없이 `받은 조건 수락`만 누르면 화면에 보인 조건 그대로의 수락이므로 질문하지 않고 체결한다. 로그에는 `skipped_no_text`로 남는다.
- 구매자 화면의 검토 상자는 멈춘 이유에 따라 문구와 버튼(`다시 추정 요청`, `검토했음 · 협상 계속`)이 바뀐다.

## 5. 로그 형식

| 키 | 내용 |
|---|---|
| `scenario`, `summary` | 제목, 심사 항목, 업무 장면 / 결과 상태, 권한 위반, 검증 없이 체결한 수(`agreements_without_verified_acceptance`), System 1 판단 수, 체결 보류, 사람 검토 이관, 승인 카드 |
| `approver`, `reviewer` | 승인자·검토자 방식과 `is_human`. fixture는 "not a person"으로 표시 |
| `episodes[].timeline` | 한국어 진행 기록. System 1 줄은 `System 1 · Zoro` 또는 `System 1 · 규칙 참조(모델 아님)`로 판독 주체를 밝힘 |
| `episodes[].system1_checks` | 판단마다 요청 해시, 질문, 답, 지연, 기준값과 출처, 결론과 이유. 모델이면 원응답(`response`) 포함 |
| `episodes[].events` | 순서대로 일어난 일: 공급사 제안, 판단, 전송, 승인, 멈춤, 재개, 합의 기록 |
| `episodes[].business` | 첫 제시를 그대로 받았을 때와 비교한 개선액, 대안 대비 실현 절감 |
| `episodes[].evidence_class` | `real_model_run` / `cpu_reference_not_model_evidence`, 장애 주입 시 `_with_injected_fault` |
| `episodes[].evaluator_only` | 공급사 숨은 값. 채점·검토용이며 에이전트 입력이 아님 |
| `provenance` | git 커밋, 입력 파일 해시, 모델 pin, 실행 설정 |

`negotiation/artifacts/20261119_scenarios_cpu/`에 보존했다. 명령은 3절의 CPU 참조와 같다(`--backend keyword`, 승인·검토 fixture). 로그의 `provenance.git_commit`은 생성 시점의 HEAD(`1b27ca5`)이며, 이 변경은 아직 커밋 전 작업 트리에 있었다. 커밋 뒤 같은 명령으로 다시 만들면 커밋이 맞춰진다. **모델 근거가 아니다.** 규칙 판독기는 정해진 단어만 읽으므로, 표현을 바꾸면 놓친다.

## 7. 한계와 아직 하지 않은 것

- 시나리오 실행기(`run_scenarios.py`)의 실제 모델 결과는 Kaggle T4에서 v1·v2를 각 1회 실행한 기록이다(6-2·6-3절). 별도로 2026-11-20에는 Brev L40S의 대시보드·체험 API에서 native Zoro-1로 시나리오 세 개를 실행했다. [당시 대화와 판독 기록](../artifacts/20261120_live_demo/README.md)
- 기준값 0.5는 맞춘 값이 아니다. 판독 정확도는 라벨을 붙인 문장 묶음으로 따로 재야 하며, 이 저장소에서는 재지 않았다.
- 범위 밖 요구를 받은 뒤 사람이 "계속"을 고르면 에이전트는 단가·납기·결제만 계속 협상한다. 선급금 같은 요구 자체의 처리는 사람의 몫이고 코드로 다루지 않는다. 다만 2026-11-20부터 그런 요구가 붙은 제안은 에이전트가 받기로 해도 바로 합의하지 않는다. 세 조건을 다시 보내며 그 밖의 요구는 포함하지 않는다고 밝히고, 공급사가 그대로 수락해야 합의한다(규칙 판독기와 로컬 Mac의 Zoro-1 1회로 확인).
- 승인자와 검토자는 fixture(사람 아님)다. 사람이 답한 기록은 `--approver ask --reviewer ask`나 대시보드로 따로 만든다.
- 각 시나리오는 합성 공급사 하나를 1회 실행한 것이다. 성능 비교나 일반화 근거가 아니다.
