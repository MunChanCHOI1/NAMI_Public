# 협상 에이전트 모델 사용 설정 튜닝 준비

기준일: 2026-11-18. **갱신(2026-11-19): SELECT 단계는 Colab T4 FP16으로 개발 120건을 실행해 설정 F2를 골랐다([SUBMISSION.md](SUBMISSION.md) 5절). 확인 구간(CONFIRM)은 아직 실행하지 않았다.** 아래 본문은 실행 전에 고정한 준비 내용이며, 분·요청 수는 추정치이고 CPU 리허설 숫자는 모델 근거가 아니다.

프로토콜(`tune-2026-11-18.v1`)은 **실제 모델 응답을 보기 전에** 코드(`negotiation/src/negotiation_agent/tune.py`)와 이 문서에 고정했다. 결과를 본 뒤 바꾸면 새 버전으로 만들고 그 사실을 기록한다.

## 1. 무엇을 튜닝하는가

고정된 Zoro-1이 내는 두 추정값을 정책이 **어떻게 쓸지**를 고른다.

- 후보별 수락 가능성 ("이 역제안을 그대로 받을까")
- 최종안 여부 ("지금 제안이 최종안인가")

바꾸지 않는 것: 모델 가중치, 모델 pin, 질문 문구, 공개 상태 표현, 정책 상수, 시뮬레이터. 모든 후보 구성이 **같은 요청**을 읽으므로 기록된 요청 해시가 그대로 유지되고, 저장한 응답 하나를 모든 구성이 함께 쓴다.

### 가중치 미세조정을 넣지 않은 이유 (고정된 공식 소스에서 확인한 사실)

- 공식 엔진은 온도를 입력으로 받는다. `decide_engine.py`는 체크포인트의 `temperature.json`(`{"text": T, "image": T}`)을 읽고 없으면 기본값을 쓰며, `/v1/decide`는 요청별 `temperature`를 받는다.
- 온도를 맞추는 도구(`kev.metrics.fit_temperature`)와 판단 head 학습(`train.py --decision_data`)은 `export_kev_checkpoint.py`의 주석에 이름만 나온다. 고정한 네 파일에는 들어 있지 않다.
- 자체 native 어댑터는 원본 `jev_head.pt`와 다른 head를 거부한다.

그래서 이번 준비는 "사용 설정"만 다룬다. 온도는 예/아니오 질문에서 순위를 바꾸지 못하고 Platt 맵에서 절편을 뺀 것과 같으므로 후보로 두지 않았다. 보정 구간에서 맞춘 값은 맵 파일에 참고용으로만 적는다.

## 2. 설계 근거: 어디에 개선 여지가 있는가

아래는 2026-11-18에 **CPU로 계산한 대역 숫자**다. 모델을 호출하지 않았고 모델 근거가 아니다. 개발 사례에서 본 뒤 계산했다는 점도 그대로 적는다.

개발 30건(dev-1100..1129), 평균 실현 절감:

| 수락 추정 | 최종안 추정 | 평균 실현 절감 |
|---|---|---:|
| 규칙 | 정책 사전값 | 284,264원 |
| 상수 0.15 | 정책 사전값 | 300,035원 |
| 상수 0.15 | 키워드 | 324,233원 |
| 상수 0.15 | 숨은 정답 | 326,988원 |
| 숨은 정답 | 숨은 정답 | 348,004원 |
| **실제 Zoro (T4 실측)** | **실제 Zoro** | **306,426원** |

읽는 법:

- **모델을 쓰지 않는 조합(상수 수락 + 키워드 최종안)이 실제 Zoro 에이전트보다 높다.** 실제 Zoro − 그 조합은 −17,806원, 90% 구간 [−41,073, +26]원이다.
- 실제 Zoro가 규칙보다 앞선 +22,163원은 두 사례(dev-1103, dev-1129)에서 나왔다. 둘 다 2라운드에 "최종안" 문장을 말하는 마감 압박 공급사다. 모델이 그 문장을 읽은 것인지 최종안 값을 전반적으로 높게 낸 것인지는 모른다. 발언 진단(GPU 미실행)이 이를 가린다.
- 개선 여지의 대부분은 최종안 추정에 있다. 새 개발 120건(dev-1130..1249)의 대역 계산에서 규칙 대비 전체 여지의 약 88%가 최종안 추정에 있었고, 완벽한 수락 추정은 그 위에 약 4천 원만 더했다.
- 방문한 개발 상태에서 모델의 수락 추정은 과소(평균 0.102, 실제 수락률 0.195), 최종안 추정은 과대(Brier 0.220, 기저율 0.133)였다.

그래서 후보는 최종안 추정의 출처와 축소에 집중하고, 수락 추정은 그대로 쓰거나 상수로 평탄화하거나 보정 맵을 씌우는 정도만 둔다. 그리고 **선택한 구성이 "모델 값을 뺀 쌍둥이"보다 나은지**를 함께 잰다.

## 3. 고정한 프로토콜

### 사례 구간

| 구간 | 사례 | 용도 |
|---|---|---|
| D0 | dev-1100..1129 (30건) | 짧은 확인과 회귀 확인만. 실제 모델이 이미 본 사례라 선택에 쓰지 않는다 |
| SELECT | dev-1130..1249 (120건) | 후보 중 하나를 고른다 |
| CONFIRM | dev-1250..1549 (300건) | 고른 구성을 한 번 확인한다 |
| CAL | calibration-2000..2059 (60건) | 보정 맵 적합 전용. 절감액을 표시·비교·순위화하지 않는다 |
| RESERVE | dev-1550..1999 | 다음 프로토콜 버전을 위해 남긴다. 이번에는 건드리지 않는다 |

평가 분할은 실행기에 지정할 방법이 없고, 실행기는 `negotiation/evidence/`를 만들지 않는다(테스트로 검사). 알려진 노출: 실제 모델은 D0만 봤다. 다만 설계 중 모델 없는 대역 집계를 dev-1130..1999에서 계산했으므로 "처음 보는" 개발 구간은 없다. SELECT와 CONFIRM은 "실제 모델로 아직 실행하지 않은" 구간이다.

### 후보 8개 (순서 고정, 동률이면 앞선 후보)

| 이름 | 수락 추정 | 최종안 추정 |
|---|---|---|
| M0 | 모델 | 모델 (지금의 에이전트, 모든 동률에서 우선) |
| M1 | 모델 | 정책 사전값 |
| M2 | 모델 | 키워드 |
| M3 | 모델 | 축소: `w×모델 + (1−w)×사전값` (w는 CAL에서 적합) |
| F1 | 상수 0.15 | 축소 |
| F2 | 상수 0.15 | 키워드, 아니면 축소 |
| M4 | 모델 + Platt 맵 (CAL에서 적합) | 모델 |
| M5 | 모델 + Platt 맵 | 키워드 |

CPU 기준 행(모델 호출 없음, 선택 대상 아님): 규칙+사전값, 상수+사전값, 상수+키워드, 규칙+키워드, 고정 양보율, 중간값, 숨은 정답 참고 상한. 각 후보의 "모델 없는 쌍둥이"는 이 중 하나다(수락 모델 → 상수 0.15, 최종안 모델·축소 → 사전값, 키워드는 그대로).

키워드를 쓰는 구성(M2, F2, M5)은 시뮬레이터가 최종안 문장을 정해진 문구로 내보내기 때문에 유리하다. 표현이 바뀌면 통하지 않는다. 이 한계는 결과와 함께 적는다.

### 규칙

- **선택.** SELECT에서 완료되고 권한 위반 0건·검토 필요 0건인 후보 중 평균 실현 절감이 가장 높은 것. 모든 후보가 끝난 상태(완료, 사유 있는 실패, 건너뜀)일 때만 선택을 기록한다. 예산으로 멈춘 후보가 있으면 선택하지 않는다.
- **확인 (1차).** `improvement_confirmed`는 다음을 모두 만족할 때만이다: 선택한 구성 S가 M0이 아니고, CONFIRM에서 (S − M0) 실현 절감 차이의 90% 구간 하한이 0보다 크고, 평균 순절감 차이가 음수가 아니고, S에 권한 위반이 없다. 그 밖에는 `not_confirmed`(기본 설정 유지), 필요한 실행이 끝나지 않았으면 `incomplete`.
- **확인 (2차, 사전 선언, 판정을 바꾸지 않음).** S − 쌍둥이의 구간 하한이 0보다 크면 `model_contribution_shown`. S − 규칙은 참고로만 보고하며 확인으로 인정하지 않는다(설계 중 규칙 대비 대역 숫자를 이미 봤다).
- **통계.** 사례 단위 대응 부트스트랩 2,000회, seed 20261116, 90% 구간. 기존 평가와 같은 설정이다.
- **보정 맵.** CAL에서 M0을 한 번 실행한 결과에서만 적합한다. Platt 맵은 기존 `fit-calibration`과 같은 방식, 축소 가중치는 0.0~1.0을 0.1 간격으로 Brier 점수가 가장 낮은 값(동률이면 작은 값)이다. 맵 파일은 읽을 때마다 그 결과에서 다시 계산해 같아야 한다. 손으로 고친 파일은 거부한다.
- **확인 구간은 상태 폴더 기준 한 번.** 첫 호출 전에 사용 기록을 남긴다. 이전 상태 ZIP을 복원하거나 새 상태 폴더에서 다시 확인하는 것은 프로그램이 알아채지 못한다. 같은 구간을 쓴 적이 있으면 그 사실을 결과와 함께 보고한다.
- **실패한 추정.** 저장하지 않고, 채우지 않고, 자동으로 다시 묻지 않는다. 실행은 첫 실패에서 멈춘다. 같은 명령을 다시 실행하면 그 구성은 실패로 두고 나머지를 이어 가며, `--retry-failed`가 사람의 재시도 결정으로 기록된다. 결과를 본 뒤 고르지 않도록 미리 정한다: SELECT나 CONFIRM에서 추정이 실패한 구성은 `--retry-failed`로 **한 번** 다시 시도한다. SELECT에서 그래도 실패하면 `board`로 실패를 받아들이고, CONFIRM에서 그래도 실패하면 판정은 `incomplete`로 보고한다.
- **한 선택은 한 절차로.** 후보들이 서로 다른 소스 파일 상태에서 실행됐으면 선택을 기록하지 않는다. 선택 뒤에 소스 파일이 바뀌면 확인 구간의 첫 사용을 거부한다.
- **끝나지 않은 첫 사용 이어 가기.** 예산이나 중단으로 멈춘 확인 구간은 프로토콜·구간·선택·저장소 식별자·소스 파일이 같고, 앞선 실행이 기록한 답이 저장소에 그대로 있을 때만 첫 사용으로 이어 간다. 확인 구간 실행 중에는 사례별 절감액을 화면에 출력하지 않는다.
- **보정 실행이 재시도에도 실패할 때.** `fit-map --declare-unavailable --reason <사유>`로 맵을 만들 수 없음을 기록한다. 맵이 필요한 다섯 후보는 실패로 끝나고 M0·M1·M2로 계속한다.
- **실제 모델 backend는 native 어댑터(`--backend zoro`)만.** `--decision-temperature 1`을 명시해야 한다. HTTP backend는 응답한 서버를 저장소 식별자에 묶을 수 없어 거부한다.

허용된 결과 문장은 `protocol.json`의 `allowed_result_sentences`에 고정했다. 예: "확인 구간에서 기본 설정보다 나아졌다는 것이 확인되지 않았다. 기본 설정(M0)을 유지한다."

## 4. 실행 방법

### Colab T4 (권장)

1. 개발 PC에서 변경을 커밋한 뒤 소스 묶음을 만든다. GPU가 필요 없다.

   ```sh
   python scripts/make_source_bundle.py
   ```

   `runs/bundles/negotiation-source-<커밋 12자리>.zip`이 생기고, **마지막 줄에 64자리 내용 해시**가 출력된다. 커밋하지 않은 변경은 들어가지 않는다.
2. `notebooks/negotiation_tuning_colab.ipynb`를 Colab에서 열고 T4를 선택한다.
3. 1번 셀의 `EXPECTED_CONTENT_SHA256`에 그 해시를 붙여 넣고, ZIP을 파일 패널에 올린 뒤 위에서부터 실행한다.
4. 7번 셀(전체 실행)은 시간 예산(기본 45분)에서 멈추고 상태 ZIP을 만든다. 다시 누르면 저장된 답을 재사용해 이어 간다.
5. 9번에서 리더보드와 선택을 확인한 뒤, 10번의 `RUN_CONFIRM`을 체크해 확인 구간을 실행한다.
6. 11번에서 상태 ZIP을 내려받는다. 런타임이 끊기면 새 런타임에서 그 ZIP을 올리고 1번부터 실행한다.

### 로컬 Windows GPU PC

노트북 마지막 셀에 PowerShell 명령이 있다. 요약:

```powershell
$state = 'runs/negotiation/tuning/local-gpu'
& $gpuPython -X utf8 negotiation/run_tune.py plan --state-dir $state
& $gpuPython -X utf8 negotiation/run_tune.py run --stage all --budget-minutes 45 --state-dir $state @zoro
& $gpuPython -X utf8 negotiation/run_tune.py board --state-dir $state
& $gpuPython -X utf8 negotiation/run_tune.py run --stage confirm --budget-minutes 60 --state-dir $state @zoro
& $gpuPython -X utf8 negotiation/run_tune.py pack --state-dir $state --output runs/negotiation/tuning/local-gpu-state.zip
```

`$gpuPython`과 `$zoro`는 [PLAN.md](PLAN.md) 5절의 값이다. GPU, dtype, 라이브러리 버전이 다르면 저장된 답을 섞지 않으므로 **Colab 상태 ZIP을 로컬에서 이어 실행하지 말고 로컬 전용 상태 폴더를 쓴다.** 로컬 RTX 5060 Laptop은 이전 실행에서 메모리가 한계에 닿았고 판단 1회가 2~19초였다. 전체 프로토콜은 Colab T4를 권한다.

### 예상 시간 (추정치, 측정값 아님)

`plan`이 출력하는 값이다. 요청당 1.75초, 개발 30건당 약 77요청(2026-11-16 T4 실행 기준)이고, 구성마다 전부 새로 호출한다고 본 상한이다. 저장된 답을 재사용하므로 실제는 더 적을 수 있다. 얼마나 적을지는 모델의 값에 따라 달라져 미리 알 수 없다.

| 단계 | 요청 수 상한 | 분 상한 |
|---|---:|---:|
| 짧은 확인 | 6 | 0.2 |
| 회귀 확인 (D0) | 77 | 2.2 |
| 보정 (CAL) | 154 | 4.5 |
| 선택 (SELECT, 후보 8개) | 2,464 | 71.9 |
| 확인 (CONFIRM, M0과 S) | 1,541 | 44.9 |

모델 다운로드·변환·로드 시간은 여기에 포함하지 않았다.

### 결과물 (상태 폴더)

| 파일 | 내용 |
|---|---|
| `protocol.json` | 고정한 프로토콜과 그 해시. 모델을 올리기 전에 기록 |
| `store/` | 모델이 답한 요청과 응답 전체(요청 해시별). 실행 환경(GPU, dtype, head 해시, torch 버전)도 기록 |
| `runs/<단계>/<구성>/attempt-*/` | 실행별 `result.json`과 판단별 `decisions.jsonl`. 덮어쓰지 않는다 |
| `maps/calibration-*.json` | Platt 맵, 축소 가중치, 참고용 온도 |
| `leaderboard.md`, `leaderboard.json` | 구성별 평균 절감, 차이의 90% 구간, 근거 등급, 실시간 요청·재사용 수 |
| `selection.json`, `selected_config.json` | 선택 기록과, 이후 동결에 넘길 설정 파일 |
| `confirm_first_use.json` | 확인 구간 첫 사용 기록 |
| `run.lock` | 실행 중인 프로세스 표시. 실행이 끝나면 지워지고 ZIP에 넣지 않는다 |

근거 등급은 결과마다 따로 붙는다: `real_model_run`(모든 답을 이번 실행에서 받음), `real_model_run_partly_replayed_from_store`, `real_model_replay_from_store`, `real_model_requested_no_model_answer`, `cpu_rehearsal_not_model_evidence`(CPU 대역을 모델 자리에 둠), `cpu_reference_not_model_evidence`(모델을 쓰지 않는 구성). 같은 요청이 한 실행 안에서 반복되면 첫 실행도 "partly replayed"로 표시될 수 있다.

## 5. 튜닝 뒤에 할 일 (이 실행기 범위 밖)

1. 상태 ZIP을 개발 PC로 가져와 원본은 `runs/negotiation/` 아래에, 작은 요약만 `negotiation/artifacts/<날짜>_tuning/`에 둔다. 문서에는 명령, 소스 해시, GPU, dtype, 온도와 그 출처, 요청 수, 실시간 초, 완료 여부를 적는다.
2. 선택한 설정을 평가 분할에 쓰려면 **로컬 PC의 한 checkout에서** 동결하고 한 번 실행한다. 동결 기록에 절대 경로가 들어가므로 동결과 실행은 같은 기기에서 한다.

   ```sh
   python negotiation/run_evaluation.py freeze <backend 옵션> --config-file <상태 폴더>/selected_config.json --output runs/negotiation/freeze.json
   ```

   `--config-file`은 파일 전체와 해시를 실행 설정에 넣어 동결한다. 선택 뒤에 고친 파일과 CPU 리허설에서 나온 파일은 실제 모델 backend에서 거부한다. 평가 분할은 한 번만 쓸 수 있으므로 실행 여부는 따로 결정한다.
3. 확인 결과로 다시 바꾸고 싶으면 RESERVE 구간에서 새 프로토콜 버전으로 고르고 확인한다.

## 6. 결과로 말할 수 있는 것

| 결과 | 말할 수 있는 것 |
|---|---|
| `improvement_confirmed` | 합성 개발 사례에서, 선택 구간에서 고른 설정이 확인 구간에서 기본 설정보다 실현 절감이 높았다 |
| `not_confirmed` | 기본 설정보다 나아졌다는 것이 확인되지 않았다. 기본 설정을 유지한다 |
| `model_contribution_shown` | 선택한 설정이 모델 값을 뺀 쌍둥이보다 높았다 |
| `model_contribution_not_shown` | 모델 값을 쓰는 것이 쓰지 않는 쌍둥이보다 낫다는 것이 드러나지 않았다 |

어느 경우에도 보류 평가 결과가 아니고 실제 협상에 대한 근거가 아니다. 모델 없는 구성이 이기는 결과도 나올 수 있다. 그 경우 그대로 보고한다.

## 7. CPU 리허설 (모델 근거 아님)

등록된 구간 크기 그대로, 키워드 규칙을 모델 자리에 두고 전체 흐름을 한 번 실행했다.

```sh
python negotiation/run_tune.py plan --state-dir runs/negotiation/tuning-rehearsal-cpu-20261118c
python negotiation/run_tune.py run --stage all --state-dir runs/negotiation/tuning-rehearsal-cpu-20261118c --backend keyword
python negotiation/run_tune.py run --stage confirm --state-dir runs/negotiation/tuning-rehearsal-cpu-20261118c --backend keyword
python negotiation/run_tune.py pack --state-dir runs/negotiation/tuning-rehearsal-cpu-20261118c --output runs/negotiation/tuning-rehearsal-cpu-20261118c.zip
```

- 네 명령 합계 약 23초(Linux, Python 3.13.18). 대역이 답한 요청은 `all`에서 538회, `confirm`에서 673회였다.
- 모든 결과가 `cpu_rehearsal_not_model_evidence` 또는 `cpu_reference_not_model_evidence`로 표시됐고 리더보드의 `counts_as_model_evidence`는 `False`였다.
- 흐름 확인용 숫자: SELECT 평균은 M0 243,099원, F1 259,888원(선택됨), 규칙 243,099원, 상수+키워드 259,888원. CONFIRM에서 F1 − M0은 +11,085원 [+6,112, +16,439]원. 여기서 "모델"은 키워드 규칙이라 F1은 상수+키워드와 같다. 이 숫자는 실행기가 판정까지 도달한다는 것만 보여 준다.
- `negotiation/evidence/`는 만들어지지 않았다. 상태 폴더는 116MB, ZIP은 5.4MB였다.

## 8. 검증 범위와 남은 위험

검증한 것 (CPU):

- 통합 테스트 714 passed, 6 subtests passed (Linux, Python 3.13.18). 테스트 수는 모델 근거가 아니다.
- 기본 동작 불변: dev-1100 1라운드 요청 해시 `17596ee5…fa16fc7`, 플래그 없는 CPU 개발 30건 평균(규칙 284,263.67 / 고정 양보율 260,145.5 / 중간값 64,341.37 / 참고 상한 348,003.93)이 그대로다.
- 보존된 실제 응답 9건(`artifacts/20261116_colab/demo_replay.json`)을 실제 어댑터 클래스의 반환 형태로 저장소·조합·정책에 통과시켜 기록된 결과와 같은지 검토 에이전트가 확인했다.
- 독립 검토 여섯 관점(첫 실제 실행, 정보 경계와 분할, 기본 동작 불변, 표기와 주장, 통계와 절차, 저장소와 재개)이 낸 문제를 코드로 확인해 고쳤다. 검토의 반박 단계는 사용량 한도로 실행되지 않아, 각 문제는 수정하기 전에 코드에서 직접 확인했다.
- 통계 검토의 귀무 모의실험(CPU, 대역 값에 잡음을 넣어 후보 8개가 기대값이 같도록 만든 경우, 600회씩): SELECT 120건에서 고르고 CONFIRM 300건에서 판정했을 때 `improvement_confirmed`가 나온 비율은 4.2%와 3.7%였다. 판정은 하한 0 초과라는 한쪽 5% 검정이고, 후보 8개 중 고르는 것이 확인 구간의 오탐률을 높이지 않았다. 대역으로 한 모의실험이며 실제 모델의 분포를 뜻하지 않는다.
- 저장소 검토: 실행 중 프로세스를 임의 시점에 강제 종료(5회 실행, 실행마다 12~41번)하고 이어서 실행해도 리더보드와 선택이 끊김 없는 실행과 같았다. 2만 줄 저장소는 1.3초에 읽혔다. 상태 ZIP의 경로 조작·변조는 모두 거부됐다.

확인하지 못한 것:

- 실제 GPU에서의 모든 것: 모델을 올린 뒤의 첫 호출, 실제 응답의 저장 크기와 속도, 실행 환경 기록, Colab의 폼·업로드·다운로드, 중지 버튼.
- 저장된 답의 재사용 비율. 구성이 바뀌면 협상 경로가 달라지므로 실제 모델에서는 대역보다 낮을 수 있다.
- Windows에서의 실행. PowerShell 명령은 인자 해석만 테스트했다.
- 잠금 파일(`run.lock`)의 Windows 동작. 한 상태 폴더에는 한 번에 한 실행만 허용하며, Linux에서는 죽은 프로세스가 남긴 잠금을 스스로 정리한다. Windows에서는 비정상 종료 뒤 잠금 파일을 직접 지워야 한다.
- 실제 차이의 크기. 개발 30건에서 Zoro − 규칙의 사례별 표준편차는 약 13.7만 원이었다. S − M0의 표준편차는 모른다. 300건으로도 작은 개선은 구간 하한이 0을 넘지 못할 수 있다.
